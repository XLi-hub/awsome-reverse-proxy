# Awesome Reverse Proxy 项目计划

## 1. 目标

本项目建立一份可维护、可解释、可复核的开源反向代理项目目录。它需要同时回答三个问题：

1. 项目是否真的以反向代理或入口流量处理为核心能力；
2. 项目适合什么场景，与相邻项目有何差别；
3. 推荐依据来自哪里，信息最后在何时复核。

第一版以 50–100 个高质量项目为目标。完整性服从准确性，不以收集最多链接为目标。

### 当前进度（2026-09-09）

- 74 个唯一活跃候选已完成 GitHub 元数据补全；
- 52 个通过首轮审核并进入正式目录；
- 22 个保留为 `needs-review`，等待许可证、范围或项目关系补证；
- 2 个归档仓库已移出活跃候选并记录排除原因；
- 候选合并、API 补全、审核应用和目录生成均可由脚本确定性复现。

## 2. 范围

### 2.1 分类

| 分类标识 | 含义 | 典型能力 |
|---|---|---|
| `general-reverse-proxy` | 通用反向代理 | HTTP 路由、TLS 终止、上游转发 |
| `load-balancer` | 负载均衡器 | 健康检查、四层/七层均衡、高可用 |
| `lightweight-proxy` | 轻量或嵌入式代理 | 小体积、单机部署、开发环境使用 |
| `proxy-library` | 可嵌入的代理开发库 | 供其他应用构建代理能力 |
| `cloud-native-proxy` | 面向云原生基础设施的数据平面 | 动态配置、服务发现、可观测性 |
| `ingress-controller` | Kubernetes 入口控制器 | Ingress 或 Gateway API |
| `api-gateway` | API 网关 | 路由、鉴权、限流、插件扩展 |
| `service-mesh-gateway` | 服务网格入口/出口网关 | 网格流量治理、策略和遥测 |
| `reverse-tunnel` | 反向隧道与内网穿透 | NAT 穿透、端口映射、隧道复用 |
| `zero-trust-access` | 零信任访问入口 | 身份感知代理、私有服务访问 |
| `proxy-management-ui` | 反代管理面板 | 可视化配置、证书和主机管理 |

一个项目可以拥有一个主分类和若干标签；第一版候选文件只记录一个最主要的 `category`，避免重复展示。

### 2.2 默认排除

- 纯正向代理、代理 IP 池、订阅转换或节点采集工具；
- 以账号中转、破解授权或规避第三方平台限制为主要用途的项目；
- 只有示例代码、课程代码或一次性配置片段的仓库；
- 未修改的 Fork、镜像仓库及无明确上游关系的重复仓库；
- GitHub 已归档、被明确弃用或 README 指向替代项目的仓库；
- 缺少可识别许可证且维护者没有说明使用条件的仓库，正式收录前应暂停审核；
- 与反向代理仅有边缘关系，主要价值属于其他领域的项目。

历史上重要但停止维护的项目可进入独立的“历史项目”附录，不参与活跃项目评分。

## 3. 项目发现

### 3.1 关键词矩阵

搜索同时覆盖仓库名称、描述、README 和 GitHub Topics：

```text
reverse-proxy       http-proxy          proxy-server
load-balancer       tls-termination     tcp-proxy
udp-proxy           ingress-controller  gateway-api
api-gateway         service-mesh        edge-proxy
reverse-tunnel      port-forwarding     zero-trust-access
proxy-manager       nginx-ui            self-hosted-proxy
```

基础查询示例：

```text
"reverse proxy" in:name,description,readme archived:false fork:false
topic:reverse-proxy archived:false fork:false
topic:api-gateway archived:false fork:false
topic:ingress-controller archived:false fork:false
```

大型结果集按 Star 区间、创建时间、主要语言和类别拆分，避免搜索结果上限掩盖长尾项目。低 Star 不直接排除，但需要更强的工程质量或独特性证据。

### 3.2 种子扩展

从已知代表性项目扩展以下线索：

- Topics 与官方组织下的相关仓库；
- README 中列出的替代品、兼容组件与迁移目标；
- 高质量 Awesome 列表和生态文档；
- 已弃用项目 README 指向的维护中继任者；
- 同类项目的公开比较文档。

Awesome 列表和搜索结果只产生候选，不能直接成为推荐依据。

### 3.3 数据获取原则

优先使用 GitHub REST/GraphQL API 获取动态元数据，网页和项目文档用于语义审核。抓取程序应：

- 使用认证请求并从环境变量读取 Token；
- 缓存原始响应，不提交 Token 或认证头；
- 读取限流响应头并实施退避；
- 确定性分页，保留查询与抓取时间；
- 自动发现记录命中的 Topic/描述信号，并以范围相关性门槛过滤明显噪声；
- 将自动字段与人工编辑字段分离。

多个 Agent 不独立重复抓取同一批 API 数据。由单一抓取任务建立缓存，分析 Agent 消费缓存或仅提交仓库标识和人工字段。

## 4. 从候选到正式收录

### 4.1 状态流转

```text
candidate → needs-review → accepted
                      └──→ rejected
                      └──→ historical
```

- `candidate`：自动搜索或研究 Agent 提交，尚未完整核验；
- `needs-review`：初步相关，但存在许可证、维护状态或定位疑问；
- `accepted`：通过人工审核，可以进入正式目录；
- `rejected`：不符合范围，并记录稳定的排除原因；
- `historical`：具有历史价值但已不适合作为活跃推荐。

### 4.2 硬性审核

正式收录前至少确认：

1. 仓库是项目的规范上游地址；
2. 反向代理、入口流量或反向隧道属于核心用途；
3. 非未修改 Fork，未归档，未被官方弃用；
4. License 可识别，或已经明确标注许可证风险；
5. 中文简介与项目官方描述和文档一致；
6. 分类、协议和部署标签有项目文档依据；
7. `reviewed_at` 是本次人工核验日期。

## 5. 评价模型

评分用于辅助排序，不替代人工判断，也不应宣称项目绝对优劣。

| 维度 | 权重 | 参考信号 |
|---|---:|---|
| 社区影响力 | 25 | Star 的对数值、Fork、贡献者与生态采用 |
| 维护活跃度 | 25 | 最近提交、最近发布、持续发布情况 |
| 工程成熟度 | 20 | 测试、CI、安全策略、版本化与升级路径 |
| 文档与易用性 | 15 | 部署文档、配置示例、架构与迁移说明 |
| 反代相关性 | 15 | 核心定位与本目录范围的匹配程度 |

评分约束：

- Star 使用对数归一化，避免头部项目完全支配排序；
- 不因 Issue 绝对数量多而直接扣分；
- 新项目可进入“潜力项目”，与成熟项目分组展示；
- 最近提交少不自动等于停止维护，需要结合发布和维护声明；
- “生产可用”“高性能”“安全”等结论必须有直接证据；
- 同分时优先展示信息完整、近期复核的项目。

评分公式和归一化边界在拥有足够候选数据后冻结，并记录版本。首轮候选阶段不生成虚假的精确分数。

## 6. 数据与输出

### 6.1 文件职责

```text
data/inbox/*.yaml       分类别研究结果，允许并行编辑
data/candidates.yaml    自动合并的统一候选池，不手工编辑
data/projects.yaml      通过审核的正式项目
data/rejected.yaml      排除项目和原因，防止重复审核
```

候选字段和正式项目字段见 `docs/DATA_SCHEMA.md`。

### 6.2 README 展示原则

最终 README 由 `data/projects.yaml` 生成，按分类呈现精简表格。动态指标标注抓取日期，重点项目补充“适用场景”和“限制”，避免空泛的“最好”“最强”。

第一版至少提供：

- 分类导航和收录标准；
- 项目名称、客观定位、主要标签、License；
- 活跃状态和最后复核时间；
- 数据与方法文档入口。

## 7. 多 Agent 协作协议

多 Agent 只并行处理边界清晰的分类文件：

- 每个研究 Agent 只写一个 `data/inbox/*.yaml`；
- Agent 不直接修改生成文件、最终 README 或其他 Agent 的文件；
- 主 Agent 负责 Schema、跨分类去重、分类裁决和最终合并；
- 有争议的项目先保留为 `needs-review`，不在并行阶段强行定案；
- 同一仓库跨分类出现时只保留一个主分类，其余能力写入 `tags`；
- 所有描述使用客观中文，不复制宣传文案，不写未经验证的比较结论。

## 8. 自动化路线

### 阶段 A：规范与首轮候选

- 建立范围、分类、Schema 和校验脚本；
- 多 Agent 分类别产生候选；
- 合并、去重并人工抽查。

### 阶段 B：元数据补全与正式目录

- 实现集中式 GitHub API 抓取和缓存；
- 补全 License、语言、Topics、Star、Fork、提交和发布信息；
- 完成人工审核，生成第一版正式目录。

### 阶段 C：持续维护

- GitHub Actions 定期刷新动态字段；
- 通过 Pull Request 展示新增、归档、转移和活跃度变化；
- 保留历史快照，用于计算趋势而非只看累计 Star；
- 定期复核长期未更新和许可证变化的项目。

## 9. 完成标准

第一版发布应满足：

- 至少 50 个正式项目，覆盖主要分类；
- 所有项目通过 Schema 与唯一性校验；
- 所有项目有明确 License 状态和复核日期；
- 动态字段带抓取时间，不将过期数据伪装为实时数据；
- README 可由数据文件确定性生成；
- 新贡献者可以仅依据文档提交一个合格候选。
